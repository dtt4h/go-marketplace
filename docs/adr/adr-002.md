# ADR-002: Выбор стека

**Дата:** 19.07.2026  
**Статус:** принято

## Контекст

Заказчику нужен MVP маркетплейса. Бюджет ограничен, команда небольшая. Важно: быстро запуститься, выдерживать нагрузку и не упереться в потолок, когда пойдут реальные пользователи.

Маркетплейс — это нагрузка на чтение (просмотры товаров, поиск, каталог) с пиками во время распродаж и акций. RPS на каталог может быть высоким даже при небольшой аудитории, потому что один пользователь листает десятки страниц.

## Решение

### Backend

| Компонент | Технология | Почему |
|-----------|------------|--------|
| Язык | **Go** | Высокий RPS на чтение, низкое потребление памяти, один бинарник. Маркетплейсы на Go держат нагрузку лучше, чем на Node.js/Python при тех же ресурсах. |
| HTTP | **Chi** | Легковесный, поверх стандартного `net/http`, не добавляет своих абстракций. |
| БД | **PostgreSQL** | Надёжная реляционная БД, хорошо работает с каталогом, фильтрами, транзакциями заказов. |
| Драйвер БД | **pgx** | Нативный протокол PostgreSQL, быстрее `database/sql`, поддерживает `LISTEN/NOTIFY`, batch-запросы. |
| Кэш / очереди | **Redis** | Кэш каталога и сессий, rate-limiting, очереди лёгких задач (email, уведомления). |
| Хранилище файлов | **S3-совместимое (MinIO)** | Картинки товаров, аватары, логотипы магазинов. Не храним файлы в БД. |
| Миграции | **golang-migrate** | Простые SQL-миграции, версия схемы в БД. |
| Логирование | **slog** | Стандартная библиотека Go 1.21+, структурные логи в JSON. |

### Инфраструктура

| Компонент | Технология | Почему |
|-----------|------------|--------|
| Контейнеризация | **Docker + Docker Compose** | Один `docker-compose up` поднимает всё: app, db, redis, minio. |
| Мониторинг | **Prometheus + Grafana** | Метрики RPS, latency, ошибки. На MVP — базовые дашборды, расширять по мере роста. |

### Почему не микросервисы на старте

Микросервисы на MVP — это оверинжиниринг. Больше времени на инфраструктуру, сложнее отладка, нужен service discovery, трейсинг. Модульный монолит на Go даёт ту же скорость разработки, а когда модуль (например, Products или Payments) упрётся в нагрузку — его можно выделить в отдельный сервис без переписывания, потому что границы уже разделены.

## Рассмотренные альтернативы

### Node.js (NestJS)
Был бы быстрее старт по фронтенд-бэкенд синглу, но RPS на каталог ниже, потребление памяти выше. Для маркетплейса чтение — основная нагрузка, и здесь Go выигрывает.

### Python (FastAPI)
Удобно для прототипа, но на нагрузке упирается в GIL и требует больше ресурсов. Для маркетплейса — не лучший выбор.

## Итог

Go + PostgreSQL + Redis + S3 — это рабочий набор для маркетплейса, который:
- держит RPS на каталоге без горизонтального масштабирования на старте;
- деплоится одной командой через Docker;
- не требует сложной инфраструктуры;
- позволяет выделить модули в микросервисы, когда появится необходимость.
